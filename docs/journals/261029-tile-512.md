# 261029 — 512 px tiles: a quarter of the writes, nothing breaks

**Question.** Can new maps be tiled at 512 px instead of 256, so an ingest writes fewer R2 objects?

**Answer.** Yes. One sheet, L7014 6150-4 (4565 × 5880), tiled both ways with `vips dzsave --layout
iiif3`, Q=85: **566 tiles at 256, 152 at 512** (3.7× fewer), 12.52 MB against 12.26 MB. Served
through the live worker under a throwaway id, all 310 tile requests a viewer can make answered 200
at the advertised pixel size, both in dzsave's `w,h` spelling and in the width-only `w,` that
OpenLayers and Allmaps send. The test prefix was deleted afterwards.

**So what.** Bet 3 (corpus): the one R2 bill so far ($4.50, 2026-10-03) was Class A writes past the
free 1M, from one L7014 ingest. At 512 px the same ingest stays well inside the free tier.
`scripts/tile_map.sh` now defaults to `TILE_SIZE=512`; existing maps are untouched.

**Prediction, written before the run:** every request answers 200 at the size it names. One cell
disagreed: `full/286,/0/default.jpg` (the one-tile top level, region `full`, width-only size) is a
404. A live 256 px map (`my-tho-w`, `full/155,`) gives the same 404, so the gap is in the worker and
predates this change; the explicit `full/286,368` and the region form `0,0,4565,5880/286,` both
answer 200, and no viewer in use is known to send the failing form.

**Not tested.** A georeferenced 512 px sheet in `/explore` (the test id had no annotation), and the
OCR crop path (`vma_core.fetch_crop_level0` reads `tiles[0].width` from info.json, so it should
follow). Check both on the first real ingest.
