# Colour pass on 1882 and 1898 together — does one run serve both?

**2026-10-01.** Question: the 1882 Plan Cadastral and the 1898 Bertaux plan are both
polychrome Saigon sheets. Is it more efficient to calibrate and run `colour_blocks.py` on
them as a pair, with one set of constants? **No.** The method is shared; the constants cannot be.

All runs: `colour_blocks.py --map-id <id> --render 4096`, default full pass, VMA IIIF, OCR
rows pooled as the script finds them. 1882 = `0e02b9d9-…`, 1898 = `20ec4f9a-…`.

## What each sheet derives for itself

| Constant | 1882 | 1898 |
|---|---:|---:|
| r−g split (crops voting) | +0.072 (20/64) | +0.087 (37/64) |
| green split, r−g | +0.027 | +0.007 |
| cool split, r−b | +0.072 | +0.027 |
| ink share of paper | 9.0% | 2.7% |
| paper peak → `cream_ink` | 0.87 → 0.80 | 0.96 → 0.90 |
| legend key alpha | 0.72 | 0.88 |
| m/px from GCPs | 0.3415 (8) | 0.3380 (9) |

The cream peak of r−g sits near +0.05 on 1882 and +0.02 on 1898. 1898's census has one
dominant mode (57.7% in a single bin); 1882's is a plateau. These are the same sheet
features the river EDA found (`work/analysis/river_pair/README.md`): different paper,
different pigment, so absolute colour cuts do not carry across.

## Cross-applying the constants

Each sheet rerun with the *other's* `--rg-split`, `--cool-split` and `--cream-ink`
(the green split has no override flag).

| Run | Features | Cream parcels | Buildings | Class mix |
|---|---:|---:|---:|---|
| 1882, own | 1887 | 1087 | 620 | admin 260 · blue 91 · building 620 · cream 815 · green 72 · salmon 29 |
| 1882, 1898's constants | 972 | **34** | 564 | admin 108 · blue 96 · building 564 · cream 109 · green 72 · salmon 23 |
| 1898, own | 2864 | 958 | 1554 | admin 329 · blue 175 · building 1554 · cream 312 · green 17 · salmon 477 |
| 1898, 1882's constants | 3371 | 523 | 1613 | admin 533 · blue 132 · building 1613 · cream 592 · green 72 · salmon 429 |

1898's `cream_ink` of 0.90 is above 1882's paper peak (0.87), so on 1882 the paper itself
reads as ink-free and the parcels leak into the street: 440,998 components "too small",
34 parcels left. Going the other way, 1882's 0.80 sits well under 1898's paper peak and
1898 lost 45% of its parcels.

**Scored on the one sheet that has hand traces** (`seg_eval`, best-match IoU; selected
traces, not precision; this is a 4096 render and not the 6144 baseline, so compare the
two rows with each other and not with the 0.343 / 0.355 in `docs/ROADMAP.md`):

| 1882 run | land_plot mean (n=24) | cover | building mean (n=17) | road mean (n=3) |
|---|---:|---:|---:|---:|
| own constants | 0.300 | 0.97 | 0.302 | 0.162 |
| 1898's constants | 0.220 | 0.67 | 0.226 | 0.005 |

Borrowed constants cost 0.08 land_plot IoU, 30 points of cover, and erase the road
proposals. 1898 has no hand traces, so its side of the swap is counts only — **its
accuracy under either setting is unmeasured**.

## Cost

Own-constants wall time at 4096: 1882 34.6 s, 1898 43.7 s, run concurrently ≈ 44 s. Census
(the calibration step) is 7.3 s and 1.7 s with the tile cache warm. Calibration is
auto-derived and already cheap; there is no shared step to amortise. Concurrency is the
only saving a "both at once" run offers, and it needs no code: two processes. The
cross-applied runs took 128 s and 16 s, which is fetch and contention variance, not a result.

## Decision

- Run both sheets **independently with auto-derived constants**. Do not add a shared
  calibration or a "transfer 1882 to 1898" shortcut.
- Share what is genuinely shared: the method and the evaluation gate. For the river, that is
  `docs/river-reconstruction.md` — paired hand-traced windows, per-sheet calibration.
- Pin `image_sha256` in each `blocks.run.json` when comparing runs; the 1898 green axis has
  moved between two fetches of one render (see the comment in `colour_blocks.py`).
- Still open: 1898 needs its own hand traces before any number on it means anything. The
  paired reference windows already planned under `river-reconstruction` would be the first.
