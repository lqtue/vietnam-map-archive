# The 1959 sheet lost a third of its street names to the dedupe

Audit of the OCR result for `34d4edb2-f7df-4c47-a65a-f6b471400396` — 1959 `Đô
thành Sài Gòn`, Nha Địa-Dư Quốc-Gia, 14000 × 10773, the two sheets stitched.
Run 2026-09-10, against production and against the on-disk run output in
`work/image-processing/results/34d4edb2…/runs/`.

Headline: **the dedupe was deleting real streets and the row count hid it.** The
DB held 452 street rows and 367 distinct street names against the sheet's own
claim of 384, which looks like a good result. Lê Lợi, Hàm Nghi, Công Lý and
Phan Chu Trinh were not among them.

## What was on the sheet before the fix

939 `ocr_extractions` rows from four runs, ~$1.03 and ~70 minutes of Gemini
across all eighteen run directories:

| run | prompt | rows | what |
|---|---|---|---|
| `2026-09-09T1555-34d4edb2` | seq-v1, two passes merged | 627 | body labels — 452 street, 70 hydrology, 45 place |
| `index-20260910` | legend-v1 | 156 | the printed index below the map, entries 1–156 |
| `idx-20260910` | seq-v1-idx | 111 | numerals spotted on the map body |
| `cellsweep-20260910` | cell-lookup | 45 | numerals, targeted by the index's own grid cell |

## The bug: four ways one label ate another

`_text_similar` in `work/ocr/scripts/ocr.py` decides whether two labels are the
same label read twice. `dedup_items` (within a run) and `ensemble_items` (across
runs) both cluster by union-find on that predicate, so a single wrong `True`
merges two rows — and, transitively, everything either of them touches. The
survivor's text is the one most passes wrote; the loser's name is gone.

Four distinct false positives, each measured on this sheet:

1. **Shared prefix, word overlap.** `"Đại Lộ Lê Lợi"` and `"Đại Lộ Hàm Nghi"`
   share two of four words, which clears the `>= 0.5` word-overlap test. Every
   pair of two-word `Đại Lộ` streets on the sheet qualified.
2. **Shared prefix, character ratio.** `"Đại Lộ Lê Lợi"` against `"Đại Lộ Lê
   Lai"` scores 0.92 as strings and 0.83 on the names alone — the prefix and the
   shared syllable are most of the characters.
3. **Fuzzy short syllables.** `"tu do"` against `"tu duc"` scores 0.80, so Đường
   Tự Do and Đường Tự Đức were one street.
4. **A bare generic bridging the graph.** A row reading just `"Đường"` is a
   whole-word substring of every street on the sheet. One such row chained **43
   different streets into a single cluster**, and the cluster's winning text
   replaced all of them. `"ĐẠI LỘ"` did the same to Lý Thái Tổ, Trần Quốc Toản
   and Tổng Đốc Phương; a bare `"Trần"` did it to the *Trần …* streets.

Measured over the three full-sheet passes: 697 distinct name-cores were read by
the model, 447 reached the DB. Of the 250 lost, 135 were multi-word real names
and 33 were read independently by two or more passes — not model noise.

Why nobody noticed: none of this fails. Every stage reports success and a
plausible count. The loss is only visible by counting distinct names against the
sheet's own printed claim, or by grepping the on-disk tile JSON for a street you
know is there.

## The fix

`_text_similar` was rewritten around two ideas: compare the **name**, not the
string, and compare it **syllable by syllable**.

- `_label_core` cuts exactly one generic prefix (`Đường`, `Đại Lộ`, `Bến`,
  `Rạch`, `Rue`, …), matched longest-first. Exactly one, because stripping a run
  of them turns `"Rạch Bến Nghé"` into `"Nghé"` and throws away the name. A
  label that is *only* a generic gets an empty core — it names no place, so it
  can no longer act as a bridge.
- `_fold` drops diacritics and normalises `đ`/`ð`, so a dropped tone mark costs
  nothing.
- `_words_similar` requires the same syllable count and a match at every
  position. `_syl_match` allows fuzz only above four characters: below that,
  folding has already absorbed the noise fuzz is for.
- The word-overlap test now needs **two** shared syllables, not a ratio. For a
  two-syllable name, 0.5 meant exactly one syllable matched.
- The substring test requires both sides to be name-like — two syllables, or one
  of five characters or more — and to have a non-empty core.
- `_close_px` replaces `max_dim * 1.5`. Proximity now scales with the **short**
  side of the box, the text's height, not its length: a 600 × 80 street label
  was buying a 900px budget and sweeping up the next street over.
  `_CLOSE_FACTOR = 4.0` is a calibration knob — measured on this sheet, 2.5 → 6.0
  moves distinct names by two and row count by 12%, because once the text test
  was right this threshold only decides how many rows one street keeps.

`work/ocr/scripts/test_dedup_labels.py` is the check: 16 pairs that must stay
apart, 7 that must join. Every one of the sixteen was collapsed before this.

## Result

Re-deduped each pass from its cached tile JSON and re-merged — no model calls,
so this cost nothing:

| | before | after |
|---|---|---|
| merged rows | 627 | 969 |
| street rows | 452 | 795 |
| distinct name cores | 456 | 607 |
| rows confirmed by ≥2 passes | 309 | 482 |

Lê Lợi, Hàm Nghi, Công Lý, Phan Chu Trinh, Lý Thái Tổ, Tổng Đốc Phương, Lê Đại
Hành, Tôn Đản, Đồng Khánh, Cường Để and Mạc Thiên Tích are all back.

Two other things came with it:

- **`idx-20260910` is now a third pass.** It was a full-sheet run — 108 tiles, 36
  calls, 23 minutes, ~$0.38, 1858 extractions — harvested for its 111 numerals
  and 94% discarded. Its street reads were still on disk. Merging them raised
  the rows confirmed by more than one pass from 309 to 482, and its own 111
  numeral rows carried `model = null, prompt = null`; both are now stamped from
  its `run_config.json`.
- **Bare numerals no longer enter the body-label merge.** They belong to the
  numerals pipeline, which writes them as `legend_ref` with the printed index's
  cell as a check. A gazetteer row reading `"112"` is noise.

### The DB write

New run `2026-09-10T0930-34d4edb2` (969 rows). Before deleting the superseded
`2026-09-09T1555-34d4edb2`, its 60 human decisions were carried across by
`_text_similar` + proximity: 26 transferred (both validations, 24 rejections),
and the 34 that did not are all rejections of duplicate numerals, which this run
no longer emits. Then the 627 old rows were deleted. The map now holds 1281 rows.

## The printed grid was miscalibrated

`triage.grid.bbox` came from margin ticks measured by hand. Only **124 of 144**
observed numerals fell in the cell their own index entry names — and 16 of the
20 misses sat within 50px of a cell boundary, one cell out in a consistent
direction. The grid, not the readings.

Refitted per axis against the 144 observations (the axes are separable, so no
joint search and less room to overfit), tie-breaking on distance from a cell
boundary:

```
[1039, 845, 11802, 9000]  →  [1010, 900, 11980, 8972]
      124 / 144                     141 / 144
```

Mean margin from the nearest boundary is 0.24 of a cell, where 0.25 is what
uniformly distributed points inside their cells would give — the observations sit
centred now, rather than hugging edges. The old value is recorded in
`triage.grid.src`.

This matters twice: the twelve entries placed by grid cell are better centred,
and `agreesWithIndex` in `/api/maps/[id]/legend-points` — whose tolerance is the
stated cell plus one cell on each side — was spending its whole budget absorbing
calibration error instead of catching misreads. `GET legend-points` still
returns the same 155 points: 143 from an observed numeral, 12 from a grid cell.

## Then the street directories were read

The `name_list` regions at `[350, 2143, 798, 7853]` and `[12852, 775, 798,
9221]` — the printed *Bảng chỉ dẫn đường phố* down both margins — held 0 rows.
They are a four-column table: the road-type word alone, the name, then **TỪ** and
**ĐẾN**, the grid cell each street starts in and the one it ends in. A range, not
a point, for every street the sheet names.

`ocr street-index` (new) reads it in overlapping horizontal bands of ~27 rows,
through `extract_labels` so it inherits the backoff, the key rotation and the
content cache — a re-run of bands already read is free, which is what made the
iteration below affordable. **15 calls, 384 entries, ~$0.03**, against the
sheet's own claim of 384 named streets. 382 rows written, positioned on the union
of their two cells with `notes` recording `grid=C9→C10`; the 2 unplaceable ones
are named in the output rather than dropped.

**And the two readings check each other.** Of 372 body labels that match a
directory row, **350 — 94% — sit inside the range the index states** (±1 cell: a
street is labelled somewhere along its length, not between its endpoints).
Neither reading knows about the other, so that one number validates the body
pass, the index pass and the refitted grid at once, and the 22 that disagree are
a review queue instead of a mystery.

This is what would have caught the dedupe bug on day one: 384 printed names is a
denominator, and 367 was never within 17 of it — the deleted streets were simply
invisible without something to count against.

**Row `J` is the inset, not a missing row.** Five directory rows and index entry
44 reference `J1`/`J2` while the sheet's printed rows stop at `I`. With 373
observations to fit instead of 144, the row set is settled: `A…I` scores 310/373,
and `A…J` matches it only with a grid 9920px tall, past the bottom of the map
body. All six are on the southern waterfront — `Bến Mê Cóc`, `Bến Nguyễn Duy`,
`Bến Phạm Thế Hiển`, `Bến Phú Định`, `Đường Rạch Cát`, `Chợ Rạch Cát` — which is
exactly what the inset at `[4634, 8747, 2338, 1249]` shows: a separate map that
continues the lettering. Both implementations return nothing for them rather
than guessing, which is right; placing them needs the inset's own grid.

`tests/street-index-grid.spec.ts` pins the new Python `_cell_rect` against the
TypeScript `cellBox` on a committed fixture, because the box columns are NOT
NULL and so the position has to be computed at write time — there is nothing to
defer to the server. It also pins the one deliberate asymmetry: only the
TypeScript side reads a run of cells (`"G H 10"`), which the browser needs and a
two-column table never states.

## What still stands

**Two directory rows are unplaceable**, both reported by name: `Đường Rạch Cát`
(`J2`, the inset) and `Đường Lý Văn Phức`, whose two cells came back blank.

**22 body labels disagree with their directory row** by more than a cell. Six of
those are the `J` cases; the other sixteen are a genuine review queue.

**Index entry 44 still gets no point.** Same cause, now with the evidence: the
inset has its own grid and `triage.grid` cannot express it.

**Numeral 49 is a misread** — read at B9 against a claimed F5, about 6 km out.
`agreesWithIndex` rejects it, which is the guard working. Nothing flags it for a
human, so it will sit there.

**`label_w` / `label_h` are null on every row.** The model returns an
axis-aligned box and an angle, not an oriented box's own dimensions, so the
mig-076 columns cannot be filled from this data. `geom` and `footprint_id` are
null too: no SAM2 pass has run on this sheet.

**Review has barely started** — 2 validated, 36 rejected, and
`maps.legend_done` is still false. The sheet now holds 1663 rows.

**One incidental fix:** a Gemini project spending cap arrives as `429
RESOURCE_EXHAUSTED`, which `extract_labels` classified as a per-minute rate
limit. Each call therefore spent the full backoff ladder — about fourteen
minutes — before failing, so a fleet run would report "rate limited" for hours
against a wall that needs a person at <https://ai.studio/spend>. It is terminal
now, with that URL in the message.

## Two lessons that generalise

**Count the corpus, not the code.** Three of the four false positives are
invisible in a code reading and obvious from one query: does the DB contain the
most famous street on the sheet?

**A silent dedupe needs a named victim.** Every stage here reported a plausible
number. The only thing that would have failed is an assertion about a specific
label that must survive, which is what `test_dedup_labels.py` now is.
